## Adversarial checks

- The client covers health, job creation, group get/update, column get/update, run start/status, result, and visualization endpoints, including APIs added after the original task was drafted.
- `FormData` requests do not manually set `Content-Type`, so the browser supplies a valid multipart boundary.
- Empty uploads remain server-validated; Unicode, spaces, and nested relative filenames are handed to `FormData` unchanged.
- Every job/group path parameter uses `encodeURIComponent`; visualization parameters use `URLSearchParams` and preserve explicit zero values.
- JSON headers are limited to POST/PUT JSON bodies and are not attached to GET or multipart calls.
- FastAPI string details remain readable; structured validation details are JSON-serialized rather than rendered as `[object Object]`.
- Non-JSON success and failure bodies are rejected with deterministic messages; a response body is read only once.
- Cancellation is not converted into an unavailable state, while an actual stopped server is displayed as `API 연결 안 됨`.
- Optional run fields match backend defaults; projection methods/dimensions and run states are closed unions.
- Result score-curve types mirror `ScorePoint` correctly and do not incorrectly require the summary-only `total` field.
- Open-ended result details remain `Record<string, unknown>` rather than an unsafe assumed schema.
- The client and types are re-exported from one module entry point for downstream consumers.
- `client.ts` is 119/200 non-blank lines, `types.ts` is 105/200, and all functions remain below 50 lines.
- No upload workflow, progress loop, job storage, backend mutation, or UI scope was introduced.
