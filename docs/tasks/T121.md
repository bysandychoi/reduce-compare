## Scope

- Add a FastAPI `TestClient` integration test for the complete API journey: upload, inspect groups, inspect/update selected columns, start reduction, poll status, and fetch the completed result.
- Verify the pre-run idle status and unavailable-result response before execution.
- Exercise the real pipeline and persisted job configuration rather than mocking endpoint internals.
- Keep job storage isolated under pytest's temporary directory.

## Non-goals

- New API behavior, production-code refactoring, performance benchmarking, browser/frontend testing, or live-server network testing.
- Repeating every validation and failure case already covered by endpoint-specific suites and T066.
- Testing visualization, future report APIs, authentication, deployment, or multiple concurrent users.
- Using private worker state as the primary success signal; the end-to-end assertion should observe public status/result endpoints.

## Technical approach

- Create `backend/tests/test_api_flow.py` with one representative dataset large enough for the real reduction pipeline.
- Upload through `POST /jobs`, then use returned identifiers and public endpoints for each subsequent step.
- Select explicit numeric/categorical columns and persist the detected group's merge decision before starting.
- Start with a zero similarity target for a deterministic, fast real pipeline run.
- Poll `GET /jobs/{id}/status` with a bounded monotonic deadline until `done` or `failed`; fail with the returned status if completion is not successful.
- Validate the final result's job-independent folder label, group name, row counts, score/method fields, and projection data.

## Acceptance criteria

1. The test creates a job via multipart upload and receives HTTP 201 with the accepted file list.
2. Group and column APIs expose the uploaded schema, and saved column/group choices are accepted before execution.
3. Before execution, status is `idle` and result lookup returns the expected 409.
4. Starting reduction returns HTTP 202; public status polling reaches `done` with 100% progress within a bounded timeout.
5. Result lookup returns HTTP 200 and a schema-valid result consistent with the uploaded row count and saved configuration.
6. The focused test, full backend suite, Ruff/compile checks, frontend regression gates, and diff checks pass.

## Edge cases and risks

- Background completion timing is nondeterministic; use a bounded deadline and short polling interval, never an unbounded wait.
- A worker failure must surface its public status payload in the test failure to remain diagnosable.
- Shared module-level executors can retain completed futures; every uploaded job has a unique ID and isolated root.
- Small or constant datasets can fail PCA or column selection; use varied rows and at least two useful features.
- Absolute temporary paths must not appear in successful API payloads.
