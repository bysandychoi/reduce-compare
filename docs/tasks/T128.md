## 조사 결과: 가드 판정과 done 게이트

**가드 판정 근거가 서로 다르다.**

| 항목 | `hooks/task_guard.py` (공용) | `.claude/hooks/task_guard.py` (포팅본) |
|---|---|---|
| 판정 주체 | `scripts/check_task_status.py`에 위임 | 훅이 직접 판정 |
| 보는 것 | `.agent/active_task`의 ID 하나 → 그 태스크의 상태 | `backlog.json`의 `in_progress` 태스크 **목록** |
| 통과 조건 | 그 ID의 상태가 정확히 `in_progress` | in_progress가 **하나라도** 있으면 통과 |
| 활성 태스크 없음 | 차단 | 차단 |
| backlog를 못 읽음 | 차단 (fail-closed) | **통과** (fail-open) |
| 위임 스크립트 내부 오류 | 차단 (`check_task_status.py`가 예외를 block으로 바꾼다) | 해당 없음 |
| **훅 래퍼 자체의 오류** | **통과** — 예외를 삼키고 경고만 내보낸다 | 통과 (예외 처리 자체가 없다) |
| 검사 대상 | `extract_file_paths`가 찾은 경로 — `tool_input`의 **모든 문자열 값**을 패치 봉투로도 스캔하므로, 쓰는 **내용**에 봉투 예시가 들어 있으면 그 안에 적힌 경로까지 검사 대상이 된다 | `file_path`/`notebook_path`만 |
| 예외 경로에 쓰기 | 내용에 봉투 예시가 있으면 **차단될 수 있다** — 봉투가 가리키는 경로가 예외가 아니면 `docs/tasks/**`에 쓰는 것도 거부된다(격리 복제본에서 재현) | 통과 |
| 도구 이름 | 보지 않는다 | 보지 않는다 (쓰기 도구로 좁히는 것은 설정 matcher의 몫) |
| 예외 경로 목록 | `hooks/config.json`의 `task_guard.exempt` + `scripts/check_task_status.py`의 `DEFAULT_EXEMPT` **하드코딩 사본** (현재 글자까지 동일) | `.claude/hooks/config.json`의 `task_guard.exempt` |
| 셸 경유 파일 수정 | **미검출** (경로를 못 찾으면 검사 없이 통과) | 미검출 |

즉 판정 로직 자체는 공용판이 더 엄격하지만(모르면 막는다), **훅 래퍼 수준에서는 양쪽 다 fail-open이다** — `tool_input` 모양이 예상과 다르면(예: `file_path`가 리스트) 공용판도 경고만 내고 통과한다.

**예외 경로 목록은 공용 트리 안에서도 두 군데에 복제돼 있다.** `hooks/config.json`의 `task_guard.exempt` 15개와 `scripts/check_task_status.py`의 `DEFAULT_EXEMPT` 15개가 글자까지 같고, `_exempt_globs()`는 config를 못 읽으면 **경고 없이** 하드코딩 사본으로 떨어진다. 그래서 config에 쉼표 오타 하나만 나도 가드가 조용히 옛 정책으로 돌아간다(정상 config면 차단되는 수정이 오타 뒤에는 통과한다). `.claude/hooks/`를 지워도 이 중복은 남으므로, T129의 완료 기준 "중복된 로직이 한 곳에만 남는다"를 채우려면 이것도 같이 없애야 한다.

**활성 태스크 파일은 정상 사용만으로도 backlog와 어긋난다.** `backlog.py`의 `sync_active_task`는 in_progress가 둘 이상일 때 마지막 ID 하나만 기록하고, 그 ID가 다른 상태로 빠지면 **다른 태스크가 아직 in_progress여도 파일을 비운다**. 또 `.gitignore`가 `.agent/`를 제외하므로 새로 clone 하면 파일 자체가 없고, `session_start.py`는 복구하지 않는다. 통합 후 fail-closed 판정으로 바뀌면 이 두 경우 모두 예외 경로가 아닌 파일(즉 애플리케이션 코드)의 수정이 "활성 Task가 없습니다"로 막힌다. `hooks/**`·`docs/tasks/**`·`backlog.py` 등 예외 경로는 그대로 통과하므로 `backlog.py status <ID> in_progress`를 한 번 돌리면 `sync_active_task`가 디렉터리까지 만들어 파일을 복구한다 — 단 의존 태스크가 아직 안 끝난 태스크면 이 명령이 exit 1로 막히므로 `--force`가 필요하다. 문제는 차단 메시지가 그 방법을 알려 주지 않는다는 점이다.

**done 게이트는 통과 조건이 같고 트리거·안내가 다르다.** 양쪽 모두 리뷰 PASS(마지막 `Verdict:`/`판정:` 줄) + 리뷰 이후 파일 변경 없음 + lint·build 통과 + 보호 브랜치 아님을 확인하고, 실패하면 `in_progress`로 되돌린다. 다른 점:

| 항목 | 공용 (`backlog_sync.py`) | 포팅본 (`backlog_commit.py`) |
|---|---|---|
| 변경 감지 | `hooks/.state/backlog_snapshot.json` 영속 스냅샷과 비교 | 워킹트리 더티 여부 + HEAD 내용 |
| git 저장소 아님 | done을 되돌린다 | 분기 없음 |
| 진척률 계산 | 0 나누기 보호 있음 | `fin / total * 100` 무방비 |
| push | `push_if_possible`로 upstream/원격 유무 분기 | 같은 분기를 함수 분리 없이 수행 |
| 반려 메시지 | 영어, 되돌렸다는 사실만 알린다 | 한국어 + "adversarial-reviewer로 리뷰를 받고 PASS가 나오면 다시 done 처리하세요"라는 **다음 행동 안내**가 붙는다 |

스냅샷 기준은 새 동작을 만든다: 다른 머신에서 done 처리한 것을 `git pull`로 받아오면 스냅샷은 과거 상태이므로, 그 뒤 **조회만** 하는 `python backlog.py list` 한 번에 done 플로우가 돌아 `git add -A` + push를 하거나 리뷰가 없다고 판단해 되돌릴 수 있다. 현재 포팅본은 워킹트리가 깨끗하면 즉시 빠져나가므로 이런 일이 없다.

## 결정

**`hooks/`를 유일한 구현으로 삼고 `.claude/hooks/`는 없앤다.** `.claude/settings.json`이 `python "$CLAUDE_PROJECT_DIR/hooks/<이름>.py"`를 직접 부르도록 바꾸고(지금처럼 절대 경로를 유지한다 — 상대 경로로 바꾸면 하위 디렉터리에서 시작한 세션에서 훅이 exit 1로 조용히 꺼진다), `.claude/hooks/` 디렉터리와 `.claude/hooks/config.json`은 지운다. 위임 어댑터(얇은 래퍼)는 두지 않는다 — 어댑터도 파일이 둘이라 또 어긋난다.

근거:
1. `hooks/`가 대체로 상위 집합이다 — 양쪽 도구의 `tool_input` 형태를 처리하고, 활성 태스크 판정이 fail-closed이며, 인코딩·팝업 처리가 포팅본보다 낫다. 다만 전부는 아니다: `guard_backlog`는 `Grep`을 과차단하면서 동시에 패치 마커가 섞인 셸 명령은 과소차단하고(같은 이유로 done 게이트의 CLI 감지도 건너뛴다), `project_root`의 마지막 분기는 깨져 있으며, `session_start`의 안내 문구는 포팅본이 더 자세하다. 이것들은 T129에서 공용판을 고쳐 흡수한다 — 고치기 전에 교체하면 지금 막히는 접근이 뚫린다.
2. 중복이 실제로 버그를 낳았다 (위 세 건). 설정 파일도 둘이라 손으로 맞춰야 한다.
3. `AGENTS.md`가 이미 "Business logic lives in `hooks/`; `.codex/hooks.json` is only a runtime adapter"라고 선언하고 있다. `.claude/settings.json`도 같은 지위의 어댑터로 맞추는 것이 일관된다.
4. 줄 수 한도 규칙도 `hooks/*.py` 하나만 남으므로 `훅 스크립트(claude)` 규칙을 지울 수 있다.

**가드 판정 경로는 `.agent/active_task` + `scripts/check_task_status.py` 하나로 둔다.** 판정 로직이 두 벌이 되는 것(포팅본처럼 훅이 `backlog.json`의 in_progress 목록을 직접 보고 따로 판단하는 것)을 되살리지 않는다는 뜻이고, **활성 태스크 파일을 채우거나 복구하기 위해 `backlog.json`을 읽는 것은 여기 해당하지 않는다** — 그 파일의 내용은 원래 `backlog.py`가 백로그에서 파생시킨 값이다.

덧붙여, 통합 후에도 안내용 훅(`session_start`·`user_prompt`·`session_end`)과 done 게이트는 `backlog.json`의 in_progress를 직접 읽는다. 활성 태스크 파일이 비면 "진행 중: T100"이라고 알리면서 같은 세션에서 파일 수정은 "활성 Task가 없습니다"로 거부하는, 문맥과 가드가 반대로 말하는 상태가 된다.

T129에서 할 일:

1. **`.claude/settings.json` 훅 경로를 `$CLAUDE_PROJECT_DIR/hooks/*.py`로 교체**하고 `.claude/hooks/`를 삭제한다.
2. **matcher는 훅별로 지정한다.** `.codex/hooks.json`처럼 PostToolUse를 `*`로 넓히면 안 된다 — `hooks/code_guard.py`는 경로를 얻는 즉시 lint를 돌리므로, **Read만 한 파일**의 기존 lint 오류 때문에 조회가 block된다. 넓히려면 `code_guard`가 "이번 호출로 실제 바뀐 파일"만 보도록 먼저 고쳐야 한다.

   | 훅 | matcher |
   |---|---|
   | `guard_backlog` | `Read\|Write\|Edit\|MultiEdit\|NotebookEdit\|Grep\|Glob\|Bash` |
   | `task_guard` | `Write\|Edit\|MultiEdit\|NotebookEdit` (`*` 금지) |
   | `backlog_sync` | `Bash` |
   | `code_guard` | `Edit\|MultiEdit\|Write` |

   matcher를 좁히는 것만으로는 부족하다 — `extract_file_paths`가 `tool_input`의 모든 문자열 값을 패치 봉투로 스캔하기 때문에, 봉투 예시가 들어간 문서를 쓰는 `Edit`/`Write` 하나로도 엉뚱한 파일이 검사 대상이 된다(13번과 함께 고친다). 실제로 13(b)가 요구하는 회귀 테스트와 문서를 쓰는 `Edit` 자체가 통합 후 거부된다.

   `task_guard`도 `*`로 넓히면 안 된다 — Claude의 `Read`도 `tool_input.file_path`를 쓰므로 `extract_file_paths`가 읽기와 쓰기를 구분하지 못하고, 활성 태스크가 없는 세션에서 `Read`가 "File modification blocked"로 거부된다(실행으로 확인). 셸을 통한 파일 수정은 어느 matcher로도 잡히지 않는다는 점은 그대로 남는다.

   알림 이벤트 이름도 다르다 — Claude는 `Notification(permission_prompt)`, Codex는 `PermissionRequest`.
3. **`hooks/backlog_sync.py:203,212`와 `hooks/code_guard.py:134`의 `hookSpecificOutput`에 `hookEventName`을 추가한다.** 지금은 빠져 있어서, 그대로 옮기면 Claude Code가 `additionalContext`를 적용하지 못해 에이전트가 커밋 결과와 줄 수 경고를 못 받는다.
4. **`.claude/hooks/`를 가리키는 문서·설정을 같은 커밋에서 고친다**: `CLAUDE.md:33`, `.claude/agents/task-briefer.md:20`, `.claude/agents/adversarial-reviewer.md:28`, `README.md:224`, `.vscode/settings.json:4`, 그리고 `hooks/config.json`의 `훅 스크립트(claude)` 줄 수 규칙 삭제.
5. **`.agent/active_task` 복구 경로를 정한다.** gitignore 대상이라 clone 직후 비어 있고, in_progress가 둘 이상일 때 `sync_active_task`가 파일을 비울 수 있다. **두 수정이 모두 필요하다**: `sync_active_task`는 상태 변경 경로에서만 호출되므로 세션 중에 비는 경우만 막고, clone 직후 파일이 아예 없는 경우는 세션 시작 때 재생성해야 덮인다(둘 다 판정 로직 추가가 아니라 파일을 채우는 쪽 수정이다). 차단 메시지에도 복구 방법을 적고, 안내용 훅과 가드가 같은 사실을 말하도록 맞출지도 함께 정한다.
6. **스냅샷 기준 변경의 부작용을 확인한다.** `git pull`로 남의 done이 들어온 뒤 조회용 `backlog.py list` 한 번에 done 플로우가 도는지 직접 재현해 보고, 필요하면 스냅샷 갱신 시점을 조정한다.
7. **훅 래퍼를 fail-closed로 만들지 결정한다.** 지금은 `hooks/task_guard.py`가 예외를 삼키고 통과시킨다.
8. 상태 파일 위치가 `hooks/.state`로 바뀐다 (`gate_max_blocks` 카운터). 이전 상태는 버려도 된다.
9. Codex에만 있던 `user_prompt.py`(UserPromptSubmit), `session_end.py`(SessionEnd)를 Claude 쪽에도 연결할지 정한다. **`session_end.py`를 연결하면 done 게이트가 거짓 반려를 낸다** — 매 세션 종료마다 추적 파일 `docs/session-log.md`에 append하는데, done 게이트의 "리뷰 이후 변경" 집합은 백로그와 `docs/tasks/**`만 제외한다. 세션 A에서 리뷰 PASS → 종료(로그 기록) → 세션 B에서 done 하면 코드 변경이 없는데도 되돌려진다. 연결하려면 제외 목록에 세션 로그를 추가해야 한다.
10. 가드가 fail-closed로 바뀐다는 점을 `CLAUDE.md`에 명시한다.
11. **포팅본에만 있는 안내를 공용판으로 옮긴다**: `session_start.py`의 `<ID>.review.md` 읽기 지시와 "`status <ID> in_progress` → task-briefer 순서" 안내, 그리고 done 게이트 반려 메시지의 "adversarial-reviewer로 리뷰를 받고 PASS가 나오면 다시 done 처리하세요"라는 다음 행동 안내(공용판은 영어로 되돌렸다는 사실만 알린다). 그냥 지우면 워크플로 안내가 사라진다.
12. `hooks/common.py`의 `project_root` git 루트 fallback은 `_run_raw`가 아래쪽에 정의돼 있어 실제로 그 분기를 타면 `NameError`로 죽는다. 통합 전에 고치거나 fallback을 없앤다.
13. **`hooks/guard_backlog.py`의 양방향 오작동을 먼저 고친다.** (a) `pattern`은 `Glob`에만, `path`는 `Grep`/`Glob`에만 적용하도록 분기한다 — 지금은 `Grep`의 내용 패턴을 경로로 오해해 보호 파일명을 언급하는 검색을 막고, Bash `grep`도 `mentions_name`에 걸려 우회 경로가 없어서 4번 같은 전수 조사 자체가 불가능해진다. (b) `extract_shell_command`가 패치 마커 때문에 명령 전체를 `None`으로 돌리는 것을 고친다 — 지금 포팅본이 막는 백로그 직접 쓰기가 통합 즉시 뚫리고, `hooks/backlog_sync.py`의 CLI 감지(done 게이트)도 같이 꺼진다. (c) `extract_file_paths`가 `tool_input`의 모든 문자열 값을 봉투로 스캔하는 범위를 좁힌다 — 지금은 쓰는 **내용**에 봉투 예시가 있으면 손대지 않은 파일이 `code_guard`에 걸리고, 예외 경로인 `docs/tasks/**`에 쓰는 것조차 `task_guard`에 거부된다. (a)(b)의 회귀 테스트를 쓰려면 이 항목을 먼저 고쳐야 한다.
14. **`scripts/check_task_status.py`의 `DEFAULT_EXEMPT` 사본을 없앤다.** 최소한 config 읽기 실패를 fail-closed로 바꾸거나 stderr 경고를 낸다.
15. 팝업 제목에 도구 이름을 넣을지 정한다 (`Claude Code · <project>` → `<project>`로 바뀐다). Claude와 Codex를 동시에 띄워 두면 어느 쪽이 끝났는지 구분이 안 된다.

## 조사 전 메모 (위 "결정"으로 대체됨)

아래는 조사를 시작하기 전에 적어 둔 것이다. 결론은 "결정" 절이고, 내용이 어긋나면 "결정"을 따른다.

- `.claude/hooks`는 Claude Code가 직접 실행하고, `hooks`는 Codex 또는 스크립트에서 호출된다 → 실제로는 두 설정 파일 모두 같은 형식의 커맨드 훅이라, 설정의 경로만 바꾸면 된다.
- 가드 판정이 두 경로로 갈린다 → 조사 결과 설계 의도는 같고 구현만 둘이다.
- 단일 진실 공급원 결정 필요 → `.agent/active_task` + `scripts/check_task_status.py`로 결정했다.
