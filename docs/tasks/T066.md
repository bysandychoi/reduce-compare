# T066 Task Analysis — API 오류 처리

## Task and dependency status

- Task: T066, API 오류 처리
- Status: `in_progress`
- Estimate: 20 minutes
- Dependency: T064 (`done`)
- Downstream task: T121
- Active branch: `dev`

## Scope

- Return a clear 4xx message when an uploaded job has no readable table file.
- Return a clear 422 message for malformed CSV input without exposing pandas parser internals or local absolute paths.
- Persist a non-empty, stage-aware user message when a background reduction fails.
- Return a controlled API error when persisted run state is missing fields, malformed JSON, or cannot be read.
- Add focused API tests covering the three backlog cases and damaged state files.

## Non-goals

- Introducing a new error-envelope schema or changing FastAPI's standard `detail` response shape.
- Frontend error presentation, localization infrastructure, logging, retry, cancellation, or cleanup.
- Changing ingestion rules, supported file types, reduction algorithms, or successful response models.
- Hiding actionable validation details such as the affected file name.

## Technical approach

- Keep `HTTPException` with FastAPI's existing `{ "detail": "..." }` shape.
- Normalize schema-discovery failures in `groups.py`: preserve concise application validation messages, but replace low-level I/O, decoding, and parser details with safe Korean messages.
- Track the current background stage in `runs.py` and format worker failures as `<stage> 단계에서 실패했습니다: <reason>`, with a fallback when exception text is empty.
- Validate persisted `run.json` through `RunStatus`; translate read, JSON, and schema failures to a controlled 500 message.
- Reuse the persisted failure message in the result endpoint.

## Acceptance criteria

1. A job with no readable table files returns 422 with a message explaining that no readable table file exists.
2. A malformed CSV returns 422 naming the affected file and explaining that its CSV format cannot be parsed, without parser details or an absolute local path.
3. A failed background job returns `failed` status with a non-empty message identifying the failed stage and reason; result lookup returns the same useful reason in a controlled 409 response.
4. A corrupt or schema-invalid run-state file returns a controlled 500 message rather than leaking a decoding or validation exception.
5. Focused API tests, full backend tests, Ruff, frontend regression gates, and diff checks pass.

## Relevant requirements

- `problem.md` §3: CSV/TSV/delimited text folders are inputs; unusable input must be distinguishable from valid tabular data.
- `problem.md` §3: when missing-value filtering leaves no rows, the cause should be explained.
- `problem.md` §7: automatic processing and result retrieval require actionable failures so the user can correct input and retry.
- `problem.md` §8: heavy work runs in the local backend and exposes progress, including controlled failure state.

## Existing and expected files

- `backend/app/api/groups.py`: normalize empty-folder and malformed-input errors.
- `backend/app/api/runs.py`: stage-aware worker failures and safe run-state loading.
- `backend/app/api/results.py`: return stored worker failures through the existing result response.
- `backend/tests/test_api_errors.py`: focused T066 error-response tests.
- `backend/app/core/ingest.py`: source of CSV validation messages; change only if normalization cannot safely distinguish them.

## Test plan

- Create an empty uploaded job directory and assert the groups endpoint returns the expected 422 detail.
- Upload a malformed CSV and assert 422 includes the file name and friendly format message but excludes parser internals and absolute paths.
- Force the worker to raise a normal and an empty-message exception; assert status and result responses remain actionable.
- Write malformed and schema-invalid `run.json` files and assert controlled 500 responses.
- Run focused tests, the entire backend suite, Ruff, frontend lint/build, and `git diff --check`.

## Edge cases and risks

- `.txt` and `.tsv` files that are not tabular are skipped; a folder containing only those must use the empty-folder message.
- Exception strings can be empty, multiline, excessive, or contain local paths. Use a bounded fallback rather than blindly exposing them.
- Atomic run-state writes avoid partial reads, but manually damaged files still require a controlled response.
- Existing clients rely on the `detail` field and status codes; preserve both.
- Successful responses must remain unchanged.
