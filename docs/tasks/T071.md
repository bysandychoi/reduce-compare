- Status: `todo` at analysis time; move to `in_progress` before implementation.
- Estimate: 25 minutes.
- Dependencies: T013 (`done`), frontend/backend proxy connection; T064 (`done`), result API.
- Downstream tasks: T073 upload connection and T080 result-page frame.
- Active branch: `dev`.

## Scope

- Add shared TypeScript response/request models for every existing backend endpoint used by the frontend: health, job upload, groups, columns, run, status, result, and visualization.
- Add one typed function per endpoint using the existing `/api` Vite proxy prefix.
- Centralize JSON decoding, FastAPI error-detail extraction, HTTP errors, network failures, and abort propagation.
- Preserve upload-relative paths by accepting `{ file, path }` records and passing the path as each multipart filename.
- Allow callers to pass `AbortSignal` for uploads, page transitions, and status polling.
- Migrate the existing health check in `App.tsx` to the shared client as an integration proof.

## Non-goals

- Connecting the folder picker to job creation, displaying upload progress, storing a `job_id`, polling, or navigating after requests.
- Runtime schema validation or generated OpenAPI clients.
- Changing backend endpoints, schemas, Vite proxy behavior, or adding dependencies/test frameworks.
- UI changes beyond replacing the direct health `fetch` with the client function.

## Technical approach

- Split models into `frontend/src/api/types.ts` and request behavior into `frontend/src/api/client.ts` to remain below TS line limits.
- Use a generic internal `request<T>` function that reads the body once, requires valid JSON for successful responses, and converts non-2xx responses to an exported `ApiError`.
- Preserve `AbortError` unchanged so React effects and future polling can distinguish cancellation.
- Convert other fetch failures to a status-0 `ApiError` with a user-safe Korean connection message.
- Encode every path parameter and use `URLSearchParams` for visualization options.
- Send JSON headers only for JSON bodies; let the browser set multipart boundaries for `FormData`.

## Acceptance criteria

1. Every current frontend-facing endpoint has a typed request function and corresponding response/request types.
2. Upload requests use multipart `files` fields and retain each selected relative path as the submitted filename.
3. JSON calls use the correct methods, paths, query parameters, and bodies.
4. Non-2xx FastAPI details become `ApiError` messages with status and detail; malformed success JSON is rejected.
5. Abort errors remain abort errors, while network failures become a consistent connection `ApiError`.
6. The application health indicator uses the shared client and retains its loading/connected/unavailable behavior.
7. TypeScript/Vite build, ESLint, backend API tests, diff checks, and line limits pass.

## Edge cases and risks

- FastAPI `detail` may be a string or structured validation array; error formatting must never produce `[object Object]`.
- A proxy or server can return HTML/empty bodies; successful malformed responses must not be silently typed as valid data.
- `Content-Type` must not be set manually for multipart requests because the browser owns the boundary.
- File relative paths can contain spaces, Unicode, or nested separators; FormData filename values must be preserved.
- IDs and group names can contain reserved URL characters and must be encoded.
- Aborted effects must not be reported as server unavailability.
- Result `detail` is intentionally open-ended and remains `Record<string, unknown>`.
